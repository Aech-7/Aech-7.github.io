Quadcopter Modelling & Control

Modeling quadcopter dynamics and developing a cascaded controller for attitude, altitude and position control.

The project

I built this project to study how a quadcopter can be modeled and controlled from its underlying dynamics rather than treating the drone as a black box. The system models the six degrees of freedom of a quadcopter — translation in x, y, z and rotation in roll, pitch and yaw.

I first developed the mathematical model and implemented the controller in MATLAB/Simulink. I then ported the system to Python and extended it with a position-control layer. This gave me a way to work through the complete process from dynamics modeling and simulation to controller debugging and trajectory control.

Modeling the dynamics

The quadcopter was modeled as a rigid body with six degrees of freedom. I used the Euler–Lagrange formulation to derive the equations of motion, including the forces and moments generated by the four rotors and the effect of gravity.

The rotor model was also included in the plant. Total thrust is obtained from the individual rotor thrusts, while differences between rotor forces generate the roll, pitch and yaw moments. The motor model relates the input voltage to RPM and then to the resulting thrust and torque.

  3. 03Rotor thrustPropeller model

The physical parameters come from the actual airframe: a 335 mm diagonal, 0.743 kg mass and 8×4 inch propellers on a 3S battery. The motor RPM, propeller thrust coefficient and torque curves are polynomial fits to manufacturer performance data, and aerodynamic drag is included as a disturbance force.

First controller

The first controller was implemented in MATLAB/Simulink. I started with attitude-rate and altitude control. PID controllers compare the desired roll, pitch and yaw rates with the current rates and generate the required control effort. A motor mixer then converts these commands into individual motor inputs.

Altitude was controlled separately through the total thrust. This gave me a relatively simple setup for first testing the dynamics and understanding how changes in motor thrust affect the attitude and vertical motion of the vehicle.

What went wrong

The initial simulations were useful not only because some of the commands worked, but because they exposed where the controller was failing. The attitude-rate controller could stabilize the vehicle for zero-rate commands and track some symmetric roll and pitch commands. However, asymmetric commands could cause the motor mixer to demand physically impossible motor inputs, eventually resulting in numerical instability.

The altitude controller could reach its target as well, but the response showed noticeable oscillation. Instead of treating these as simply tuning problems, I used the simulations to identify the limitations of the control structure and the physical constraints that needed to be represented in the model.

Porting to Python

I then ported the system from Simulink to Python using NumPy, SciPy and Matplotlib. Instead of keeping the whole system as one simulation model, I separated it into a plant model, controller, simulation loop and visualizer. This made it easier to modify the controller and test different parts of the system independently.

I also added practical constraints to the controller. Throttle was limited to its valid range, attitude-rate commands were bounded, and motor voltage was constrained to the available 0–11.4 V range. Anti-windup handling was added to prevent the integral terms from continuing to accumulate when the actuators were saturated.

Position control

Once the basic attitude and altitude control was stable, I extended the system with an outer X/Y position controller. The controller uses PI control with velocity damping to generate desired roll and pitch angles. These commands are then passed through the existing attitude and rate-control loops before reaching the motor mixer.

This created a cascaded structure where each layer has a different job: the position controller decides how the vehicle should tilt, the attitude controller tracks that orientation, the rate controller stabilizes the angular motion, and the mixer converts the resulting commands into individual motor inputs.

  • X / Y positionOuter PI controller
  • Roll / pitchAttitude controller
  • Angular ratesRate PID
  • Motor inputsMixer

Debugging the coordinate frame

One issue appeared when testing the new XY position controller with a non-zero yaw angle. The position demand was initially being interpreted directly in the body frame, which meant that the same command could produce the wrong world-frame motion depending on the drone's heading.

I fixed this by rotating the XY position demand using the current yaw before converting the desired position error into pitch and roll commands. This was a useful reminder that the controller is not only about tuning gains — the reference frames used by each layer have to be consistent as well.

  1. World frameX / Y position target
  2. Yaw rotationTransform position demand
  3. Body frameDesired pitch / roll

Current results

The tuned altitude controller can now reach a 20 m target without overshoot while maintaining zero attitude error and keeping the motor voltage within the specified range. The newer XY controller is able to perform position manoeuvres, although the larger 5 m moves are still fairly aggressive and require further tuning.

The current simulations show tilt angles reaching around 12°, angular rates around 65°/s, approximately 1.2° of yaw deviation and around 0.4 m overshoot on larger position moves. I have also added a 3D visualizer showing the drone trajectory, shadow, target and current state.

Simulation

The Python simulator now provides a fixed-step step() and reset() interface, making the controller easier to test and reuse in future simulator or reinforcement-learning environments. The command-line interface also allows different control modes and trajectories to be tested without changing the core simulation code.

What I learned

This project helped me understand that designing a controller is more than choosing PID gains. The dynamics model, actuator limits, control allocation, coordinate frames and controller structure all affect whether the system can actually behave as expected.

The transition from Simulink to Python was particularly useful because it forced me to understand the individual components instead of relying on a block-diagram implementation. The next step is to validate the Python implementation directly against the original Simulink results and continue tuning the XY position controller for smoother trajectories.
